How do we evaluate the performance of long-context LMs? Let's first introduce the popular "loss in the middle" phenomenon. The "loss in the middle" phenomenon is that the accuracy is pretty high at the beginning and end, but accuracy in the middle is pretty low. High accuracy when the relevant information appears at the start or at the end of a context, but very low accuracy when the relevant information is in the middle of the text. The key insight is that a very fluent long-context response doesn't imply you can remember the stuff in the middle. It's highly possible the language modeling perplexity is pretty good, but you're forgetting the thing in the middle. Therefore, perplexity is not enough; we need more rigorous evaluation to understand the capacity and performance of long-context LMs.

We'll introduce two benchmarks: one is "needle in the haystack," the other is LongBench. "Needle in the haystack" is a pressure test for large language models under long text. How does it work? Given those benchmarks, let's see how we improve the inference of long-context large language models. Let's first recap the concept of KV cache, which we learned in the previous lecture. The KV cache grows linearly as the number of tokens increases, so it's multiplying the mini-batch size, number of layers, number of KV heads, the dimension, the length of the sentence, K and V (two elements), and the precision. So it's two and a half megabytes for each token in the 70-billion-parameter model. When the batch size is one, sequence length is 512, that's 1GB; size of 16, sequence length 4k, that's 160GB—like 200 GPUs. This KV cache size will grow linearly with the batch size. Sometimes it can even easily surpass the model size.

We'll introduce three techniques to solve this problem of large KV cache size. The first technique is streaming LM and attention sync; the second technique is dual attention; and the third technique is query-aware sparsity.

We observed an interesting phenomenon called "attention sync"—starting from layer two, the first token is very heavily attended. This is the attention map: the first token is all red. Let's see how that works. First, observe the attention map and see what we are actually attending to. There are roughly two kinds of heads. The sentence here is, "Best fruit is orange. The other kind of head only attends to itself, the local tokens, and the first token. What if you try to prune some of the heads? If you try to prune only the retrieval heads, the accuracy will drop very quickly—if you prune 20%, accuracy goes to nothing. But if you prune the streaming heads, the accuracy will stay pretty much unchanged. If you prune randomly, that's something in between. The insight is that not all the attention heads need to do full attention—attend to everything. We can categorize all the heads into two groups: one is retrieval head, which is the original dense attention (focus on important tokens from earlier tokens in the sequence—basically, anything can attend to anything); the other kind is streaming head, which only focuses on the recent tokens and the attention sync tokens. It only needs a very small KV cache—the size is equal to the number of attention syncs (which is no drop before) and also the recent tokens, which is constant no matter how long your conversation goes. The window of attention of streaming head stays the same.

The solution of dual attention is to apply a full KV cache to the retrieval heads and use a very lightweight, constant-size cache for the streaming heads. The retrieval heads' KV cache grows linearly with the sentence length, versus the streaming heads only keep the sync (in yellow) and the most recent tokens, which is a constant size of the KV cache.

Let's see how we train alpha so that we can determine whether a head belongs to an attention head (streaming head) or the retrieval head. We expect the algorithm should be very simple, such that we can train it using just a few GPU hours—hopefully just one GPU. Here, the algorithm is very simple: we train using both the full attention and streaming attention, but mingle them together with a learnable parameter, which is alpha. Assign a trainable gate to each head, and the gate (alpha) will blend the full attention and the streaming attention, allowing the model to learn which heads are necessary—should be full attention versus could be streaming attention. Here we get alpha times full attention plus (1-alpha) times the streaming attention. The difference between full attention and streaming attention is the mask: full attention uses the causal mask, streaming attention uses this lambda-shaped mask. Then we try to distill them by minimizing the difference between using full attention versus the mixture of this combined version using skill attach. We regularize them by making those alphas small and try to add these losses together with the attention loss and regularization loss.

Because for GQA you have fewer heads for the K and V—you are sharing a lot of tokens to share the same KV, so the number of heads is smaller and it's harder to prune since you have multiple heads sharing the same KV head. A natural question is: what if we combine that with KV cache quantization? Dual attention is—you can think of it as pruning and sparsity; we can remove lots of the attention scores. That wraps up the dual attention for long-context large language model inference. We can accelerate both the prefeeding stage and the decoding stage using two kinds of KV cache: one is the streaming head, one is the retrieval head.

Let's talk about another technique: query-aware sparsity to accelerate long-context large language models. Three years ago, we found sparsity appears naturally in large language models. For example, in the sentence, "I bet the video game is a lot more fun than the film," these are the keys—some of the tokens receive a lot of attention, like "video" and "game," which are heavily attended, but some of the tokens like "I," "the," across different tokens, are not very heavily attended. The cumulative importance for "the" is pretty low, so we can safely remove these tokens, which shows that the KV cache has a lot of redundancy—we don't need to keep all the tokens in the KV cache.

Sparsity appears in the KV cache, but previous efforts have some limitations. For example, compared with dual attention, they keep all the contextual tokens, which is pretty memory intensive—you have to grow the KV cache linearly with the context size. Some query-agnostic sparsity, like fixed pattern sparsity (like StreamingLM, H2O), once a token is evicted from the KV cache, it can never come back. If it is gone, then it's gone. So we keep the token based on past information—if this token is not important here, it will never be important in the future. Similarly, for this token, once it is pruned based on the previous information, when future tokens come, it will never recover. Although it solves the memory issue, the accuracy is pretty low.

Query-aware sparsity basically says the sparsity pattern should be dependent on which token you are currently decoding. Evicted tokens can still be attended by future tokens. For example, the second token at this time step is evicted, but at the next time step, it can recover. So it can save both memory and also keep very high accuracy. That's the idea of query-aware sparsity—the sparsity pattern of the KV cache should be dependent on the new query token which you are decoding.

Let's see an example of why query-aware sparsity is crucial. This sentence is "A, B, C, D is upon this moment." "A" is "B, C, D." Token "B" is not critical at this moment—you see the attention score associated with token "B" is very blue at this moment. But as you go deeper, "A is B" suddenly becomes very important because the result should be "B." You decode the next token to decode is "B." So although previously at this moment "B" should be evicted based on the cumulative attention score, at this moment "B" should reside in the KV cache—you cannot prune it. This shows the criticality of dynamic pruning—it is highly dependent on the input query vector Q rather than static information.

What Quest does is use this query-aware sparsity in the attention mechanism. We keep everything in the KV cache, so we don't save the memory capacity, but we save the memory data movement. We only fetch those KV pages if they are important; otherwise, we keep them in memory but don't fetch them, so we reduce a lot of data movement.

How do we do that? When a new query comes, this is 1 by D (the dimension in this case is 8). We have many KV pages; at each page, we may have like 16 tokens (actually 4 in this case, but actually might be 16 or 64). This dimension is the hidden dimension—8 in this case. Two colors indicate K and V. First page, second page, and as the sequence gets longer, you have more pages. We try to compute which page in the KV cache is crucial; if it's not crucial, we should prune away some of the KV pages. How do we prune it? A golden model would be you just multiply the query with each key and see which one is promising, but that testing is just too computation-heavy—you already did all the computation, so even if you prune it, it doesn't save you much.

A smarter idea is to find some representative key and value. For these four tokens (actually 16, but in this example, four), we find the element-wise mean key and element-wise max key. The large dot product only happens if this query is dotted with this mean key or max key. This is the element-wise product with mean key, this is with the max key, and then we find the pointwise max between the mean and max. The red one is the largest, and we sum it up as the number to represent the importance of this whole page. If this is large, the page is important; if small, then we can prune away this page. It still resides in memory, but we don't fetch it from memory, so we reduce a lot of data movement.

This is how we put it in code: when we are inserting a new token in the KV cache, we first find the mean key and max key. When we are performing the self-attention, when a query comes, the query will be dot-producted with mean and max, then find the max between those to see whether this page is important.

Next, I'm going to quickly talk about beyond the Transformers—what are some of the non-Transformer architectures that are efficient, starting from state space models. In attention, roughly you have two tasks: one is to compute the information between the tokens, and the other is the transformation within a token. The state space model can handle the sequence communication as another alternative to this multi-head attention mechanism. It's very similar to RNN except that there's no nonlinearity right here.

There are three matrices: one is the A matrix, which controls the state transition from h\_{t-1} to h_t; the B matrix maps the input to hidden state; and C maps this hidden state to the output. Just using this naive state space model, you can expand this equation such that you can represent it by a convolution—it's very simple to implement.

The new work, Mamba, introduced the selective state space model. Rather than without any selectivity (different tokens have the same importance), with selectivity it can allocate different importance to different tokens—like "I want to order a hamburger," "hamburger" is given a lot of importance. That is achieved by tweaking A, B, C and making them input-dependent. So these A, B, C matrices are all functions of input X. That creates a problem—previously, since we have no nonlinear function and A, B, C are constant, you can expand h1, h2, h3 recursively and actually implement that in a convolution very easily. Linear recurrence can be implemented as a global convolution.

However, with selectivity, the A, B, C will change depending on the input, so it can no longer be implemented by convolution. How do we solve this problem of slow training? Luckily, the parallel scan is one of the implementations we can borrow, similar to computing the prefix sum: 4 + 1 is 5, 4 is 10, 4 + 1 + 5 + 3 is 13. The prefix sum is a very classic algorithm that can be implemented efficiently by parallel hardware using the parallel scan algorithm—calculate the first two (1 and 2), three, four, then one, two, three, and four in a parallel manner. We can do that similarly for computing the hidden states—remember, to compute 0 and 1, 2 and 3, 0, 1, 2, and all together, parallelize them using compute in space rather than serializing in time.

Later, there are several hybrid models combining the Transformer layer versus the Mamba layer—even the mixture of experts we talked about. Some of them are used in Transformer, some in the M version of a Transformer, and you can do architecture search to stack different components.
