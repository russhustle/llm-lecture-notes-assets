However, for the attention mechanism, we need to attend the first part of the document with the second part, first part with the third part, second with the third part, etc.—that's an n by n matrix, which requires a lot of communication. You cannot just do the attention locally; if you do it without any communication between GPU1, 2, and 3, what's going to happen? Everything can only attend locally: chapter one will not see chapter two, chapter three will not be able to see chapter two. We cannot mingle the data anymore; say you want to correlate something that happened in chapter two with chapter three—you cannot do that. Only chapter three with chapter three, chapter two with two, chapter one with one. That's too bad.

Let's see how we solve this problem. I'm going to introduce two methods; feel free to come up with a third one for your final project. Solution one is a popular technique called DeepSpeed releases, which is very widely used these days to repartition the data in the attention layer. How do we do that?

This is the QKV transformation matrix. We have three tokens, just as an example: one, two, three. We feed token one to GPU1 (background in blue), token two to GPU2 (background in green), and token three to GPU3 (background in yellow). GPU1, 2, 3 all share the same QKV transformation matrix. By multiplying this 2x3 matrix with the 1x2 input, we get 1x3 for Q, K, and V. So far, so good: each GPU is responsible for only one third of the tokens (in different colors).

Now, we want to do the attention, which requires the first token to attend to the second part, second to the third part, etc. How do we do that? We want all-to-all communication here. For all the queries, previously in GPU1, 2, and 3 for the different heads (we have three heads in this case: light green, dark green, and green), now we want to collect everything related to the dark green into the third GPU, everything related to the light green in the second GPU, everything in the normal green in the first GPU. Each GPU is responsible for one part of the head. Now we are partitioning in the head dimension; previously, we were partitioning in the sequence dimension (along the sequence: blue, green, yellow). Now we are partitioning the head dimension: head one, two, three (green, light green, dark green). GPU1 is responsible for head one (everything related to green), so we collect everything in the first column (first head), everything to GPU1, so that we can compute the QKV attention—complete attention for all the sequence. It contains token one, token two, token three. Everything related to the first head for the entire sequence is now in GPU1, everything related to the second head for the entire sequence is in GPU2, everything in the third head for the entire sequence is in GPU3. We do the attention computation separately.

Where does the communication happen? Communication happens here: we need all-to-all communication. Previously, each GPU had green, light green, dark green; now GPU1 has everything related to green, GPU2 everything related to light green, GPU3 everything related to dark green. The number of GPUs equals the number of partitions in sequences, and we chop the sequence into three parts, so we have three GPUs, also equal to the number of heads (in this example, three heads).

What's the limitation of this approach? Because you have to first calculate the QKV transformation, you have to calculate this matrix multiplication before calculating the QKV transformation, and therefore in the middle you have to do a communication to exchange data so everything related to head one is gathered in GPU1. That's exactly the case: GPU1 only has head one, GPU2 only has everything for head two, but you cannot have that here, because here we're partitioning the sequence on different GPUs. Not here: GPU1 has all the heads, but only related to the first third of the sequence, last only first third. That's why we need this shuffle. The all-to-all communication is pretty heavy here. Within a node, that's pretty good (NVLink, NVSwitch), but communication between nodes is very expensive. The other limitation is: what is the max amount of parallelism we can have for sequence? You can have a limited amount of segments, but for the head, you have a limited number of heads: 32, 16, 8—that's the limitation. The max amount of parallelism you have is limited by the number of attention heads in the model, which is a fixed number after the model is trained.

That's the OAS approach. Let me introduce a second solution, also quite popular, called ring attention (from Google's paper, also mentioned in a Berkeley paper). It's a powerful approach. We want to communicate such that GPU1's sequence can also attend to GPU2, GPU1 also wants to see GPU3. Does it remind you of the ring all-reduce? Ring all-reduce: you have a ring—GPU1, 2, 3, GPU1, 2, 3—form a circle. In the first cycle, we just rotate by one third, such that we can communicate between GPU1 and 2, so that we are no longer computing only the diagonal but also attending between the first third and the second third of the document. The first third of the document, previously on GPU1, now GPU1 and GPU2 switch, and see here: previously it's 1, 2, 3, now it becomes 3, 1, 2. The second third of the sequence now resides on GPU1. Still within GPU1, we do the attention, but now we are attending the blue document with the green one (first third with the second third). In another cycle, we rotate one more time, such that GPU1's query will be multiplied with the orange document (last third). We compute the attention in this corner. Put it together: previously we only had the diagonal part (blue document attends to blue, first third to first third), now third attends to second third, then first third attends to last third. Now we complete the whole attention process. Previously, a lot of places were white (attention not computed), now we fill in the white with color (attention computed). In another cycle, we fill in everything—computation complete.

That's ring attention: using ring attention to perform sequence parallelism in this way. It's not limited by the number of heads as the max amount of parallelism we can have, but this can effectively increase the context length during training and inference. One interesting part: recently we've been combining these two methods. One is the repetition in attention layers, versus this ring attention, into a 2D parallelism. By combining them, since within a node, GPUs have higher bandwidth of communication compared with between nodes, between nodes we can use ring attention, within a node we can use the OAS method. In that way, we can effectively perform 2D parallelism by combining these two parallelism methods to utilize the hierarchy between nodes versus within a node. That paper is called Longformer—feel free to check it out, it's also open source.
