As we have seen, matrix multiplication is a very basic building block, but convolution is a little different from matrix multiplication: it has six for-loops rather than three. The question is: how can we use matrix multiplication to implement convolution, and how do we exploit GEMM (generalized matrix multiplication) to implement convolution? Im2col is a very common technique. Here we have input activations and four kernels, and we have four output channels. We can expand the input activation from a, b, c, f, g, h, k, l, m; they all convolve with filter 0, 1, 2, 3, 4, 5, 6, 7, 8. We lay out the memory in this way: a, b, all the way to m, b, c, all the way to n, which will be multiplied with kernel 0, 1, 2, 3, 8, so that we can have this row multiplied to this column: blue, green, yellow, etc. Lay them out in this way, we can turn a matrix multiplication to implement convolution. The dimension here is K^2 \* C; if K is a 3x3 kernel, this will be 9 by C, and here is also 9 by C. Nine elements in one kernel, and C number of kernels.

That's how we use matrix multiplication to implement convolution. The pro is that this is very simple, but the con is that it requires additional memory usage. For example, we have a lot of duplication from a, b, c, f, g, h, k, m versus b, c, d, g, h, i; we have six elements that overlap with each other, so that's the drawback: additional memory space. But this can be optimized by using implicit GEMM to solve the additional memory problem: we directly operate on the input weight and activation tensor without having to lay them out and materialize them in memory.

Next optimization: in-place depthwise convolution. Depthwise convolution is very widely used. For example, here it has three components: 1x1 conv2d, 3x3 depthwise conv2d, followed by 1x1 conv2d, and each channel is operated independently. By independently, we mean channel one is only related to input channel one, channel two is only related to input channel two, and so on. If we use naive implementation, we have to allocate double the size of CHW: input plus output, so the total memory footprint will be input plus output, which is 2*CHW. What we found in the MC2 paper is that we can do in-place depthwise convolution, which is basically allocating a temporary buffer. When we are working on the first channel, we write it to this buffer, do the compute, and then write it back to the first channel. When we're computing on channel two, we also use the same temp buffer and write it back to channel two, etc. In this way, we don't need to double the memory footprint, but only need the constant, which is one channel buffer: 1+C*H, previously it was 2\*CHW.

Next optimization: memory layout matters a lot. We are going to compare the NHWC and NCHW memory layouts, and which one is good for convolution: depthwise convolution versus pointwise convolution. These are all about data layout and memory management, since data movement is super costly. As a principle in computer architecture, we want to minimize data movement, so how to allocate the data becomes super important.

The first slide is about using NHWC for pointwise convolution. What does that mean? This is the input activation: height is three, width is three, we have ten channels. NHWC means the inner loop is the channel, so we are storing 0, 9, 18, 1, etc., continuously in memory. The weight we convolve with is, since it's pointwise convolution, only 1x1 in XY dimension. Let's compare NCHW versus NHWC. N is the batch dimension, C is the channel dimension (here we have ten channels), H is the height, W is the width. Here we have height and width in the inner loop, so the layout would be 0, 1, 2, 3, 4, 5, 6, 7, 8, then 9, 10, 11, etc.—that's the NCHW layout. Versus if C (the channel dimension) is in the inner loop, what's going to happen is we are going to store 0, 9, 18, all the way to 81 in memory, then the second channel, which is 1, 10, all the way to 82, etc. If we use the NCHW manner to perform 1x1 convolution, which needs to access 0, 9, 81, 0, 9, 18, 27, 81, there's a lot of non-continuous memory access, so it's not efficient. But if we store them in NHWC manner, the channel dimension is laid out in memory sequentially, so we can take advantage of a lot of cache hits. That's why NHWC, with the channel in the inner dimension, is very good for pointwise convolution.

But for depthwise convolution, the story is completely different. This is the kernel for the weights: we have ten channels, and this is the output activation. We have a temporary buffer. We first compute the blue, then the green channel. If we use NHWC, the channel in the inner dimension, we have 0, 9, 18, 81, 0, 9, 18, all the way to 81—they are continuous. But if you use NCHW, everything green will be laid out first, then red, then gray. For depthwise convolution, using NHWC, there will be a lot of discontinuous memory access for the red, and for NCHW, the memory access will be continuous. So for depthwise and pointwise, they actually prefer very different memory layouts.

Finally, let's take a look at Winograd convolution to reduce the number of multiplications and speed up computation. Here is an example of computing an output with a 3x3 kernel interacting with a 3x3 input. We can move it in the horizontal and vertical dimension to produce four different outputs: r0, r1, r2, r3. How many multiplications are needed to produce four outputs? For every output, we need nine multiplications (3x3), so altogether, four outputs times nine multiplications times C channels: 36C multiplications to produce four outputs.

What if we have a magic transformation? Assume this transformation is free. We transform the data to a 4x4xC tensor, and the 3x3 filter becomes 3x3xC. Transform the filter, and then we just do pointwise multiplication: that's only 16 multiplications to produce an intermediate output. Then, we assume we have a free output transformation to get this out: a 2x2 output. In this case, we only have 4x4xC, which is 16C multiplications to produce four outputs, which is 2.25 times fewer multiplications compared with direct convolution. That looks pretty exciting.

What does the data transformation look like for the input, for the filter, and for the output? We write convolution with several magic matrices to do such transformation. We do the filter transformation: this is the filter, and this is the input. We do the data transformation offline using the G and B matrices. The G matrix consists of only 0, 1, 1/2, -1/2, which can be easily implemented by shift (1/2 is basically shift by one bit). This special transformation matrix consists of only 0, 1, and -1, so no multiplication is needed here, only shift is needed. Output transformation, the A matrix, only 0, 1, -1, so no multiplication is needed too. That's why the total number of multiplications is reduced from 36 to only 16: 4x4, 16 element-wise multiplications.
