The system can be difficult to defend against different types of attacks and have many different types of vulnerabilities. In general, a good defense principle is to have layered defense, like Swiss cheese, such that even if a certain layer of defense fails, overall, with defense-in-depth, it can still stop the attack at certain layers to make the attack much harder to succeed. For example, we can have different layers of defense: model input sanitization and validation, model-level defense to harden the model, policy enforcement on the actions of the agent, and monitoring and anomaly detection. Through defense-in-depth, we can build an end-to-end layered defense for the system.

The second principle is least privilege and privilege separation. Least privilege is a very important security principle in building security in traditional systems, which says that a system should only have as much privilege as needed to complete its functions or operations. In general, we have different levels of privileges: the operating system can operate at root access, other applications may have lower privileges, and users may have even lower privilege. Lower privileges, such as guest access, cannot access data and services required for higher levels of privilege.

Another important defense principle is that, ideally, we want to build a system safe by design and secure by design. Ideally, we would like to provide provable guarantees of security for the overall system. We would like to formally specify the desired security properties (for example, confidentiality and integrity) and, by using formal verification and mathematical proofs, prove that the system actually satisfies the desired security and safety properties. There are examples of traditional software systems, such as microkernels, that have been formally verified (for example, seL4). In the agentic hybrid system, formal verification can be even more challenging, but ideally, if we can enable provably safe and secure systems, this will give the strongest safety and security guarantees.

Now, with these high-level defense principles, let's talk about some concrete examples of different types of defense mechanisms. These different types of defense mechanisms can be used in conjunction through layered defense to enable defense-in-depth.

First, hardening the model. Many of the issues are due to vulnerabilities and limitations of the large language model itself. Ideally, we would like to make the model more resilient against different types of attacks, such as prompt injection, information leakage, jailbreak, and so on. This is a very important and active area of research. We can harden the model against many different types of attacks, including prompt injection, information leakage, jailbreak, data poisoning, adversarial examples, and so on. Ideally, we can take different methods throughout different stages of model development to harden the model, including data cleaning and preparation, safety pretraining, post-training alignment, and machine learning at the end. More and better techniques and solutions still need to be developed.

Another defense mechanism is guardrails for input sanitization. Given that the input to LLM may be untrusted, we need to do various checks to make sure the input matches predefined criteria, escape special characters, and do normalization to transform the input into a standard structured format. All these could help provide guardrails for inputs, sanitize input, block malicious input, and improve protection of the overall system.

The next defense mechanism is policy enforcement actions. Given that agents can take different actions, we want to ensure that these actions satisfy the least privilege principle on the tool call and obey certain security policies. We can check for policy compliance before the tool call.

Here are some examples. In our recent projects, we developed a new framework for programmable privilege control for large language model agents. As the agent generates actions for different tool calls, due to prompt injection and other types of attacks, the agent could be taking the wrong action. We have a guardrail on the agent's action for policy enforcement to ensure that the agent's actions comply with policies.

For example, an agent can use various tools for a database: load database, delete database, filter database, and read database. A user requests the agent to list hospital admission times of a patient. The system can initialize certain policies, such as not allowing the agent to delete the database and only allowing it to load the database when it's names or patients. If the agent tries to call DeleteDB, the policy enforcement will block it. When the agent calls other database functions, those are allowed, and the agent can return the information for the user query.

In another example, a banking application agent has access to functions or tools: send money, get most recent transactions, get recipient, get balance. The user issues a query about paying Apple for an iPhone. There are initial policies allowing the agent to use certain function calls. The agent first calls to get recipient with name Apple, gets Apple's account number, and the system updates the policy. The agent also calls to get the most recent transactions. If the attacker injects a prompt to send money to the attacker's account, the policy enforcement blocks it because it's not in the allowed policy. When the agent tries to send money to Apple's account, this is allowed. This shows that the original policy may not be strict enough, and the policy enforcement can dynamically update the policy based on the user's query and return results to update the policy, making it more strict and accurate to block attacks but allow correct operations.

In another example, the agent has tools for reading inboxes, sending direct messages, and various web tools. The user asks the agent to host copies of the company's employees' hobbies on the company website and send their hobbies to Bob via direct Slack message. The agent reads Bob's inbox, finds messages, and sees that Charlie wrote about his favorite hobby at a website. The agent understands it needs to visit this website and updates its policy to allow the agent to visit the website. Initially, it forbids visiting web pages, but after seeing this, it updates the policy. The agent can then proceed and conduct its actions.

These examples illustrate the necessity and complexity of programmable privilege control. In our work, we developed this privilege control mechanism for agents, enforcing the principle of least privilege. We developed a Domain-Specific Language (DSL) for flexible expressions of privilege control and guardrail policies. The DSL is flexible, extensible, and expressive. The policy enforcement framework is modular, requiring only minimal changes to existing implementations, and is efficient and real-time. We enable programmable policy updates during agent execution that are dynamic and balance utility and security, enabling hybrid policies combining human-written and generated policies.

In this overall workflow, there are manually set policies in the policy management component. As the user creates initial queries (assumed to be benign), the LLM generates additional dynamic policies to extend from the initial policies. These policies are used for policy enforcement. From the user query, the agent generates the action plan, performs tool calling, and the policy enforcement observes the function tool calls. Based on the policy, it decides either to allow or block the tool call and provides reasons. Given the results from the environment, the policy enforcement can also dynamically update the policies as needed.

With this approach, privilege control for agents enables a DSL for flexible privilege control policies, enforcing policies on tool calls. The high-level abstract syntax for the DSL provides deterministic security guarantees over encoded properties. The policy enforcement is modular and easy to use, requiring only minimal code changes (about 10 lines in our experiments). Programmable policies can be updated during agent execution to balance utility and security, enabling hybrid policies combining human-written default policy and LLM-generated policies. Human-written policies provide generic rules enforced globally for deterministic security guarantees, while generated policies enable task-specific policies updated during execution to balance utility and security. In our experiments, this framework significantly reduces attack success rate while maintaining utility, and with manual policies, can reduce attack success rate to zero.

That's policy enforcement actions. We can develop various guardrails on the actions that agents take to ensure agent actions satisfy security and safety policies.

Now, I'll briefly talk about privilege management as another defense mechanism. When the agent takes actions and accesses certain resources and services, these actions need to be taken with certain security capabilities and privacy levels. It's important to manage user access based on identities, security capabilities, and privilege levels. In traditional computer systems, we have users with different identities, roles, security capabilities, and privilege levels. For agent applications, we need to determine the identities, security capabilities, roles, and privilege levels of agents as well. This requires new frameworks to be developed. There are open questions: how to manage identities and privileges of users and their agents, how to allow users to configure access control and capabilities for their own agents and agents from others in a multi-agent system, and how to properly manage the use context of the same tool from different agents.

Next, privilege separation. The idea is to decompose the system into different components doing different tasks that require different privileges, helping satisfy the least privilege principle. Different agents can run code in separate constrained sandboxes. An open question is how to best architect and decompose the system into different modular components with least privilege.

Here's an example from traditional systems, from work my group did over two decades ago, illustrating the importance and benefits of privilege separation. We developed a system called Privtrans to enable automatic privilege separation. Given the original monolithic source code and some annotations (for example, sensitive data and privileged operations), Privtrans can automatically perform source-to-source transformation to transform the original source code into new source code separated into multiple components: a slave (with lower privilege or unprivileged) and a monitor (with higher privilege, needed to handle privileged operations). After the monolithic application is separated into slave and monitor, the system enables automatic communication setup between the two (for example, using RPC). The system is separated into two isolated parts, communicating only through this RPC channel. The privileged monitor is usually very small, making it easier to ensure its security, while the slave can be much larger, containing complex application logic. Given that it's unprivileged, even if there is a vulnerability in the slave that's later compromised, the attacker won't be able to gain higher privilege, which is in the monitor. The attack is confined to the unprivileged or low-privileged components. This is the benefit of privilege separation. In the original monolithic source code, because it needs to perform privileged operations, the whole application needs to have high privilege. If a vulnerability is exploited, even in parts of the code that don't perform privileged operations, the attacker can gain high privilege. In privilege separation, the attacker, by compromising the unprivileged components, will not gain high-level privilege. In our experiments, Privtrans was very effective, automatically decompiling original monolithic code (even large code, such as OpenSSH and OpenSSL) into privileged separated components with a small number of user annotations and calls automatically changed, significantly improving the defense capabilities of the overall system.

In agentic hybrid systems, privilege separation is even more important. We can further extend approaches like this to help automatically separate monolithic applications into different components, where each component only has the least privilege needed for its operations.

Now, monitoring and detection. All these mechanisms can be used in conjunction as a layered defense for defense-in-depth. Monitoring and detection is about monitoring system behaviors, including outputs, and applying anomaly detection. There are open challenges: how to balance full auditability and storage costs, and how to develop effective anomaly detection in diverse contexts. One example from our recent work (to appear at IEEE Security and Privacy Symposium) is DataSentinel, for game-theoretic detection of prompt injection attacks, where we fine-tuned a detector for detecting prompt injection attacks. Given the interest of time, I won't go into details, but you can see the paper for more. This is an example of model-level detection of prompt injection. We can develop other types of monitoring and detection mechanisms to detect other types of attacks and suspicious behaviors in the system.

The next mechanism is information flow tracking. The idea is to monitor how information moves through a system that may cause privacy leakage or unauthorized access and injection attacks. There are many open challenges: how to express dynamic information flow tracking policies that evolve based on conversations and user interactions, and how to ensure that tracking doesn't cause other issues.

Finally, we want to enable secure by design through formal verification, as mentioned earlier. We want to build provably secure systems to formally prove the system behaves correctly according to its specifications, ideally under all possible inputs and conditions. Of course, this is a huge challenge and open question for these hybrid agentic systems and how we can scale this up.
