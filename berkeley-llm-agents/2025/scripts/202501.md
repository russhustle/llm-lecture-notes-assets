Before we talk about more advanced prompting techniques, let's first review the background about standard prompting. In standard prompting, let's say we want to solve a math problem as shown on the slides. Before the line of works on chain-of-thought prompting, the common practice was to just put some question-answer pairs into the prompt. The question is the math question, and the answer is the final answer. Before the advancement in post-training techniques, if we directly applied standard prompting, the performance was pretty poor on reasoning benchmarks. The fundamental issue is that if we look at these standard few-shot exemplars, they only provide information on the final solution format, but they don't tell the model about the rationale to derive the solution.

Now, imagine that if you are taking a class and the teachers are basically just teaching you with the final, official solution without any more context, then if you do not have relevant background knowledge yourself, it will make your learning a lot more difficult.

For chain-of-thought prompting, the idea is that we will include these few-shot exemplars with thoughts. Again, let's take a look at this example of solving math problems. Instead of exemplars, we will provide calculation steps to demonstrate to the model how we should derive this solution step by step to achieve the final answer. After giving these exemplars with chain-of-thought rationales, the model is able to solve the problem correctly.

In practice, how these models can benefit more from chain-of-thought prompting compared to standard prompting is also dependent on the model's fundamental capabilities. On the slides, I'm showing the scaling curves presented by the original chain-of-thought papers and some other related papers about chain-of-thought properties. Among the different model families, one common trend is that CoT performance improves more significantly with the increase of the model size. In the follow-up work called "Large Language Models are Zero-Shot Reasoners," they further find that even with pre-trained only large language models, we do not have to provide the model with exemplars to elicit CoT generation. Instead, we can achieve this with an instruction. In the paper, they demonstrate the instruction, "Let's think step by step." After we apply this instruction, before we ask the model to generate the answer, the model can also generate some thoughts before generating the final solution. Empirically, they demonstrate that zero-shot CoT significantly outperforms zero-shot performance, especially on harder math and symbolic reasoning tasks. Zero-shot CoT is more convenient than few-shot CoT in the sense that we no longer need to manually annotate thoughts ourselves as exemplars. But if we compare their performance, zero-shot CoT performance is still much worse than few-shot CoT.

A very natural question is, how can we get the best of both worlds? How to get CoT performance without manually labeling exemplars? This is what we want to achieve with our paper, "Large Language Models as Analogical Reasoners," published at ICLR last year. The idea is that, instead of directly providing the model with exemplars, we instruct the model to first recall relevant exemplars to solve the test problem. Then, based on these model-generated exemplars, the model will try to solve the test problems. Imagine that these self-generated exemplars are just some CoT examples provided by external sources. The benefit of this design lies in two folds. First, these exemplars are self-generated by the large language models, so we fulfill our original goal: we don't need to do any manual labeling here. On the other hand, because this instruction is applied to each test question, for different test questions, the model is able to generate different exemplars which are more relevant to the concrete topics covered in the test question. These exemplars are more tailored to individual problems.

We call our approach analogical prompting because this methodology can be motivated by human analogical reasoning. If we think about few-shot prompting, it is not so natural if we think about it in the human reasoning way, because humans are not explicitly given demonstrations every time for each single new problem. Instead, humans also intrinsically recall from past relevant experience. In a classic reasoning methodology book called "How to Solve It" from Polya, there is a very nice description about this reasoning method named "do a related problem." The idea is that when solving a problem, we look for a previously solved problem, which is linked to our present one by generalization, specialization, or analogy. We want to learn from these past results or their methods, so that it can help us solve new task problems better.

If we think about it from the human reasoning perspective, then besides exemplars, we can also instruct a model to generate some higher-level knowledge, which can be a better summary of what we need to solve new problems. This generated knowledge can complement the problems with broader insights. Let's take solving coding problems as an example. Given a new coding problem, we can first instruct the model to self-generate some knowledge, which is more of a higher-level tutorial about the algorithms we need to solve the problem. The model needs to identify what are the main algorithms we need so that it can come up with related examples of problems with their corresponding code. After this instruction, and once the model has generated related background knowledge including higher-level tutorial and exemplars, the model goes back to solve the initial test problem.

In the results, we show that analogical prompting not only outperforms zero-shot CoT, but it actually outperforms manual few-shot CoT as well. We show this performance improvement on math problem solving, code generation, and also BIG-Bench reasoning tasks. If you look at these results for the first time, you might be a bit surprised because all these examples of problems or knowledge are generated by the model. Intuitively, it might contain more errors than human-annotated exemplars. Empirically, we indeed observe this trend. For example, for low-stakes exemplars generated by the model for math problems, around 70% of them are accurate and relevant. But the rest can have some issues: they are completely irrelevant, or there are some actually wrong calculation steps. But even so, there are some noises in the demonstrations, the model still benefits a lot from it.

Given this finding, you might imagine that this means at least the model should be able to generate some reasonable exemplars, or otherwise it cannot learn from it at all. Based on this intuition, we also conduct a rough scaling study for analogical prompting. Here we are comparing models among different GPT text model families. Given this observation, a very natural question is how we can reduce this manual work for writing prompts. One idea is that since our large models can solve many challenging reasoning problems and answer other queries, why don't we also use them to help us do prompt engineering or prompt design in general? In ICLR 2023, there is a paper called "Large Language Models are Human-Level Prompt Engineers." The high-level idea is to apply a large model to propose prompts, so that we hope these model-generated prompts can also perform even better than human-written prompts.

Here I'm showing a complete diagram of their method. There are two important stages. The first is proposal generation, where we can leverage a large language model to generate initial instructions, given our task description. Once the model generates different proposed prompts, we score each instruction based on the prediction correctness on a small set of problems. Here, we hold out a small validation set, which can tell us the quality of each prompt. The setup might be more similar to the traditional machine learning task where we have this separation of training and test, but actually we do not need to include so many examples here for this validation purpose. In most cases, it is sufficient to include tens of examples or just around 100 problems.

In our work published at ICLR last year, we go further. We try to use the language model not only to propose some instructions and do some kind of search and mutation, but also as an optimizer to iteratively improve the prompt. The idea of our approach is to instruct the LLM to leverage the past optimization trajectory represented as sorted solution-score pairs, so that it can learn to iteratively generate better prompts with more steps. In this work, we frame it as a more general optimization framework in the natural language space. In this specific use case of prompt optimization, this means that we will have two large language models as optimizers and evaluators. The optimizer is the language model, which is responsible for proposing a new instruction, given old ones and the task samples. The evaluator is the scorer, which will evaluate the accuracy or performance of a given instruction.

Let's take a look at how we can design a meta-prompt to achieve this goal. On the slides, I'm showing an example meta-prompt for GSM8K to solve math problems. The prompt itself looks pretty long, but there are two main components. The first one is the optimization trajectory, including the instructions we have explored in the past steps, with their corresponding accuracies. In practice, we sort them in ascending order and can remove older ones if the context is not enough to put all of them in the history. We also provide exemplars to show what's the task we want to optimize. For example, for math problems, we only need to include QA pairs with the final answer. Again, there's no need to annotate any train-of-thought or any explanations of how we can derive this solution.

For the results, we are testing all these instructions on pre-trained only large language models. We use prompt tools at that time. We also try using different models as optimizers, including PaLM and GPT models. For all these approaches, we are starting from the initial instruction "let's solve the problem," which achieves an accuracy of around 61% for this GSM8K task. This is a pretty general-purpose instruction. It is around 10% lower than the instruction "let's think step by step." Another perspective is that with this type of LLM-based prompt optimization, it doesn't only save us time so that we do not need to spend so much time manually tuning the prompts ourselves, but actually, when it comes up with new prompts, it also provides sometimes surprising different angles. Now let's go back to Chain-of-Thought. From the methodology perspective, what does Chain-of-Thought really bring into our reasoning? Why is it so effective? Chain-of-Thought prompting is basically giving us a way to perform variable computation of the process, which will lead the number of tokens used per problem to be adapted to tasks of different difficulty levels. In standard prompting, for the same task, if the answer lengths are the same, then if we just provide the final answer directly, it basically means that we are forcing the model to use the same amount of time, same amount of inference time budget to solve each problem, regardless of its difficulty. But with Chain-of-Thought, it shows that for more complex questions, because they also require more reasoning steps to solve the problem, like for math problems, it might require more calculation steps. With Chain-of-Thought, it allows the model to also perform more reasoning steps in the token space so that it can better solve the task problems.

In the Chain-of-Thought paper, they also show that even if the difficulty of the problems in the exemplars are pretty simple math problems, the same approach can also generalize to test problems that require much more reasoning steps. If we think about the high-level reasoning strategies, Chain-of-Thought also incorporates a lot of reasoning processes that are very important for us humans to reason about difficult tasks, such as decomposition, planning, etc.

If you want to further improve the model performance, and especially if we know some good guidelines on the reasoning strategies we need to use for a specific task, we can also explicitly instruct the LLM with the desired reasoning strategies for problem solving. One idea to further push this decomposition strategy is called least-to-most prompting. The goal of this approach is to achieve easy-to-hard generalization by explicitly telling the model what's the best practice to decompose the original problem.

On the slides, I'm showing an example for solving math problems. In the original least-to-most prompting paper from my colleagues at Google DeepMind, it includes two stages. In the first stage, it performs problem reduction. Given a math problem, it first reduces the problem into simpler subproblems. Each sub math problem can be easier to solve and requires fewer calculation steps. Given these subquestions, the model will be able to sequentially solve these subproblems and combine the solutions to solve the original problem.

The most impressive results from this work is that with least-to-most prompting design, it shows for the first time that we do not need to design neural-symbolic frameworks or require any program execution, but can still solve compositional generalization benchmarks with nearly perfect accuracy. The results shown in their paper are on the SCAN benchmark. SCAN is synthetic data about translating programmatically generated natural language commands into action sequences. The most challenging part of this benchmark is the length split. In their test splits, all the action sequences are longer than the training samples. This makes it very challenging for traditional sequence-to-sequence learning if we directly do this training on their training set. On this length split, the test accuracy will be no more than 25% unless we apply some neural-symbolic techniques. But with least-to-most prompting, they show that if they use the latest models at that time, which is code-davinci-002, they are able to achieve nearly perfect test accuracy. At the same time, they only need to use 0.1% of the training samples as exemplars. So it is both data efficient to adapt to new tasks while also the performance is very competitive.

In our follow-up work published at ICLR last year, we further show that we can extend the least-to-most prompting idea to solve more complicated compositional generalization in the case of translating text to more realistic programming languages. On the slides, I'm showing an example of translating natural language questions to SPARQL queries. The main challenge here is that for more real-world languages, including natural language or programming languages, there are more complicated grammar rules and the vocabulary size is larger. This means that, especially if we do not have a model with a super long context, a single prompt will no longer be enough to cover all the grammar rules needed to solve the task. With this challenge, it shows one benefit of decomposition: by allowing the model to use different prompts for different reasoning stages, it also enables the model to use customized prompts for each subproblem or each subtask in the context of agent development.

Here is an overview of our dynamic least-to-most prompting approach. Some details do not matter too much here, like how we do the decomposition. The main stage we add is dynamic selection of exemplars for each subproblem. For each test sentence, we can discover example questions with the most relevant grammar rules. We can assure that for each part of the sentence, we can always retrieve the most useful grammar rules to solve the task so that the model can have enough context to solve the problem. On these compositional question benchmarks, the CFQ data set, we show that our dynamic least-to-most prompting approach outperforms all these baselines, where we need to train a model on the complete training set. If we compare this dynamic least-to-most prompting with Chain-of-Thought prompting and other prompting approaches, it also scales better when we increase the number of exemplar problems to generate these few-shot exemplars.

So far, we have talked about how we can instruct the model to solve the problem with some reasoning strategies indicated by the few-shot exemplars. For different reasoning tasks, they can require very different reasoning structures. There will be different ways to decompose the task and plan for each stage. At the same time, we might not want to annotate all these best practices for each type of task. Again, we don't want to do manual labeling of exemplars for every single problem.

In our self-discover work, published at NeurIPS last year, we instruct the model to compose task-specific reasoning structures without manually written demonstrations. In practice, we list a catalog of best practice reasoning strategies, including Chain-of-Thought reasoning, decomposition, self-reflection, etc. Given a new task, the model will think about how it can utilize the reasoning strategies that are best suited for the current task and compose the reasoning structure, then follow it to solve the problem. For evaluation, we show that with this self-discovery methodology, it outperforms Chain-of-Thought prompting and other baselines on different benchmarks, including BIG-Bench-Hard reasoning tasks, MATH benchmark, and some other benchmarks for social-agent reasoning.

This thought process can adapt to tasks of different difficulty levels. We talked about how to improve Chain-of-Thought performance at inference time. In the original Chain-of-Thought paper, we talked about the few-shot prompting idea with labeling of thoughts. We talked about instruction prompting to trigger Chain-of-Thought generation. We also talked about how we can instruct a large language model to automate the prompt design and discover better prompts by themselves.

Notice that best practices of interacting with large language models can evolve over time. For example, recently with post-trained large language models, you do not have to put exemplars for every single task for the model to learn how to do it. For some models, it is better to just provide very clear guidelines and instructions on what you want, and hope the model can just follow your instructions. Some models prefer interactive discussion, and some models might prefer just a very long and detailed instruction at once. But the principles of how to discover good prompting strategies for reasoning still hold. Now, let's start the second part about performing search and selection from multiple candidates and increasing the width to explore the solution space.

After the first part, what is missing so far? I guess this question is not so hard since I already showed the outline of these slides. Basically, from the first part, we can see that we should not limit the large language model to generate only one solution per problem. The model can just have some mistakes in its single-pass solution. Instead, we should allow the model to explore multiple branches, which will allow the large language model to recover from mistakes in a single generation.

There are two ways to increase the width of this solution exploration. One is to generate multiple candidate solutions per problem. Another is that, at each step, we can allow the model to generate multiple potential next reasoning steps. It is not hard to think that with multiple sample generation, the upper bound of the performance will be definitely higher because we allow the model to select an alternative, probably better solution. The fundamental challenge for approaches along this line is how to select the best response from multiple candidates. In real-world use cases, we do not have an Oracle scorer at inference time. For example, in the chat interface, we can just have the model generate multiple solutions and the user can pick whatever they want. This is kind of a best-of selection case. But it would be more ideal if the model could do this process internally so that we do not have to review tens of solutions ourselves to select what we want.

Along these lines, I want to first talk about the self-consistency work from my colleagues at Google DeepMind. If we look at this idea nowadays, we will find that this is an incredibly simple idea, but it is actually very effective. It can improve performance a lot with all the different models. Let's say we want to solve a math problem. This time, we allow the model to generate multiple responses. After we have all these responses, we still do not know which one is accurate. Here, we have this consistency-based selection criterion. For a math problem with a single number as the final answer, we look at these three solutions. Two of them have the answer 18 and one has the answer 26. 18 is the most consistent answer, so we pick the response corresponding to this most frequently appeared answer. Note that this selection is only based on the final answer, not the reasoning process. The model can come up with whatever reasoning process it wants. As long as they lead to the same final answer, we consider them to be all good. This is a simple idea, but it boosts performance across different models and benchmarks. In their paper, they also evaluate all the models available at that time, especially on math problems, and show very significant performance improvement.

Now let's talk about this scaling effect again with the self-consistency approach. For the baseline in the curves, they compare with sample-and-rank baseline. This is a pretty natural baseline, which says that we can select the response with the highest log probability. Here, the assumption is that if the model gives higher probability to the current response, it should be more confident about it. But if we look at these curves, we can see that self-consistency performance scales much better than probability-based ranking. With more and more responses, like up to 40 responses, self-consistency performance is still improving. But these sample-and-rank baselines have already stopped improving around 10 responses. There is an exception: if we train the model to be a very good verifier for the task we care about, we might be able to outperform this scaling curve with self-consistency. We will talk about it later.

Another very important factor that contributes to self-consistency's success is that we need the model to generate very diverse responses to perform this consistency-based selection. In their results, they also compare with different baselines. Beam search is a very classic search algorithm in the NLP literature before the LLM era. At each decoding step, we keep the top k tokens with the highest probabilities. In the end, we use the sentence with the highest overall probability. They also compare with sample baselines, where they apply greedy decoding among different variants of how you formulate the prompt. Earlier we mentioned that LLMs are sensitive to different prompts. They also compare the performance to different ways to permute the exemplars' orders in the prompt. Again, they show that self-consistency using sampling scales better with more samples. The important factor here is that for the sampling method, it needs to ensure that the responses are very diverse. We can do this sampling with a high temperature, or we can perform nucleus sampling by setting the parameters in the right way to enforce this diversity, etc.

One analysis from this work is pretty interesting. It is related to model calibration. This is about how this consistency-based selection improves model performance. What does it mean when the model, for a given task, can come up with a more consistent response? They show a curve to show the correlation between accuracy and consistency. If, among sampled responses, more of them lead to the same final answer, this means that the consistency percentage is higher. There are two conclusions here. One is that this large language model is more certain with its final predicted conclusion, even if they are coming up with the same conclusion with different reasoning processes. Empirically, we see that this aggregated solution for more consistent responses can be more likely to be accurate. The final solution can just be the right one for the original test problem. This can also explain why consistency can be a simple but powerful criterion to select the final solution.

In the self-consistency paper, they demonstrate this approach on text-based reasoning problems. This consistency-based selection approach is also very powerful for code generation. In our AlphaCode work at Google DeepMind, the AlphaCode system itself is a pretty complicated one. It includes model training and inference time techniques. Here, I will mainly focus on the inference stage called filtering and clustering. Especially, this clustering is basically code selection based on the consistency of execution results.

Let's briefly discuss the background, the problem setting of competitive programming. In a competitive programming problem, the problem description includes a very long and complicated task to tell about the background story, about what we want for the corresponding code. It also includes a few input-output pairs as test cases. For the solution to be considered correct, the generated code needs to pass both the given test cases in the prompt and usually some held-out test cases. These test cases are typically of larger scale and will be more difficult than the example test cases. They will cover some corner cases.

Since we already have some input examples, we can filter the programs that fail the given test cases. For the remaining programs, they might still fail on the held-out test cases. For those of you who have participated in these coding contests, you might feel the same way. You feel that your code is great, but it just fails on some mysterious held-out test cases and you didn't get the score you want.

For the AlphaCode system, we train an LLM model to generate new test inputs for these test problems. We execute those sample programs on all these model-generated inputs. Then we cluster all programs with the same outputs together. The assumption here is that if we have the model generate enough number of test inputs, and they are diverse and of higher quality, we can assume that all programs in the same cluster are semantically equivalent because they lead to the same execution results. Finally, we sample one program from each of the 10 largest clusters. In our evaluation, we show that this clustering provides additional performance gain compared to the filter-only method. Clearly, there is still a gap from the Oracle selection, because there's still no guarantee that the consistent response will be just the best one out of the candidate pools.

Now let's revisit this self-consistency decoding pipeline. One limitation here is that for the original self-consistency, we need an answer extraction process so that we can do this aggregation among the candidate responses. If we want to apply this consistency-based decoding to broader use cases, the natural next question is how we can do it for free-form generation, where it is not natural to have this aggregation and answer extraction process. This is what we want to achieve with our work on universal self-consistency. The idea is that, instead of having this answer extraction process, we ask the large language model to perform consistency-based selection. Specifically, we throw an instruction to the model asking it to select the most consistent response based on the majority consensus, and it needs to take a look at all these candidate responses. The intuition here is that, clearly, we know that it will be hard for the model to judge the answer correctness by itself, but consistency should be a simpler criterion to measure.

Empirically, we evaluate this universal self-consistency method for different applications. For low-stakes, free-form generation problems, like summarization and question answering, where we stack low factual final answers, we see that universal self-consistency still improves over the baselines, where the original self-consistency is not directly applicable. On math reasoning and coding problems where we can apply the original self-consistency idea, universal self-consistency can match its performance without the requirement of performing answer extraction and code execution. Notice here, universal self-consistent performance is bounded by the long-context capability. At that time, we were using an earlier model, which was not super great at long-context reasoning. We can see that when we include more responses in the prompt, the performance might not go up as well as the original self-consistency. But with the recent development of long-context models, this will allow such model-based selection approaches to scale more with more responses. In practice, for most tasks, it can be well-solved within, let's say, 10 responses in the candidate pool. This still showcases the usability of this model-based consistency selection.

Previously, we talked about, for model-based selection, using the log probability from the original model. This approach of ranking doesn't scale better than the consistency-based selection. To improve further over this consistency-based selection, one idea is to train a large language model as the ranker. We hope that at least this ranker can perform better than this simple consistency criterion. It can have some sense of which responses are more likely to be accurate.

On the slides, I'm showing a diagram from the original OpenAI paper, which introduced the GSM8K data set. They demonstrate this method of how to train a verifier to judge the correctness of the math solution. Later on, they have a follow-up paper called "Let's Verify Step by Step." For this line of LLM-based ranking works, there are two ways to design the LLM-based method to judge answer quality. The first way is the initial and most standard approach, called outcome-supervised reward model. It verifies the correctness at the solution level. Given a math problem and the solution, the model will tell you whether the solution is correct or not. Another approach introduced in "Let's Verify Step by Step" is called process-supervised reward model. Instead of verifying at the solution level, we can also verify at a step level, to see whether each step is accurate. In their work, they show that this process-supervised reward model actually scales better with more samples compared to the outcome-based reward model and the majority voting baseline. Clearly, here, the performance will be highly dependent on the verifier quality. The same verifier might not generalize across tasks. We know that the consistency-based criterion is very simple and can be directly applied to many tasks. For these ranking models, you need to design a good training strategy and training data so that it can really work across different domains you care about.

So far, we have talked about response selection only at the solution level. We only perform this selection after the full responses are generated. Assuming that we have a very good step-wise scorer, then solution-based response selection is a waste of using this step-wise scorer. We can do more with such a more powerful and fine-grained verifier. If we really have this good step-wise scoring function, we can perform tree search with large language models. Instead of waiting until the solution becomes complete, during the search process, we can prioritize exploration of partial solutions at the step level. We can explore more promising steps before exploring other processes.

On the slides, I'm showing a diagram from the Tree of Thought prompting paper. From this illustration, you can clearly see the differences of different prompting methods. Chain-of-Thought prompting is basically a chain. The self-consistency method is like multiple parallel chains. For Tree of Thought, at each step, it can have multiple branches to explore the next step. You don't have to complete all these step passes until the end.

I'll show how we can apply the Tree of Thought idea with a simple example of the game of 24. At each step, there are two important stages. One is thought generation. In this step, we prompt the large language model to propose possible next thinking steps. In the game of 24, these next thinking steps are pretty simple in format. You just need to select the two numbers to perform the calculation. The other stage is thought evaluation. Here, we can prompt the large language model to evaluate how promising the current state is. For the game of 24, you need to decide whether it is possible to reach the final number of 24 after all the manipulations.

Previously, we showed how we can do evaluation at the step level. It will determine the quality of each individual step. Related to our previous consistency-based selection discussion, for this scoring function, we can also think about it as a way to just select the best state among the candidates. We don't need to just have the model make this decision at the point level. The idea is that we can ask the large language model to select the best responses among all possible next steps. We can also do this voting multiple times. Since all these steps here are based on large language model sampling, with all these different votes, the model can finally select the majority vote as the final choice to proceed.

For the results, I'm showing the game of 24 evaluation. In the original paper, they also show some other benchmarks. We can see that with Tree of Thought using breadth-first search, it scales better than standard prompting and Chain-of-Thought with respect to token budget. Going further, we can integrate more advanced search algorithms. In the original Tree of Thought paper, they use the most basic BFS and DFS algorithms. Later, we also see some papers coming up with Monte-Carlo Tree Search methods. Some works are also trying to train a separate evaluation function instead of just prompting the model. Here, the important consideration is that we need to design a good language model and prompting scheme so that it can be effective for self-evaluation.

To summarize, in this second part, I showed that we can further scale inference time compute by sampling multiple branches in the solution space. We talked about consistency-based selection, which is a simple but effective and general principle. We talked about self-consistency, where we can marginalize out reasoning processes and do selection based on the final answer. For code generation, we can also do reranking based on execution consistency. When large language model self-evaluation works well so that it can really judge the quality of partial solutions or structure quality at a step level, we can also apply search methods. In this case, sometimes, it will scale better and can reduce the token cost because it can already eliminate non-promising processes during the mean time.

Finally, I will talk about iterative self-improvement, which will try to increase the depth to reach the final solution. Even with the most recent advanced models, including those recent models, we can see that they can achieve pretty amazing numbers on competitive and challenging benchmarks for solving hard math and coding questions. But they can still, sometimes, make pretty obvious mistakes and people keep complaining about it. If you think about us as humans, we also tend to make sometimes pretty trivial mistakes at first thought. Previously, we talked about sampling multiple solutions to help us reduce these mistakes from a single prediction. If we think about it again, it is actually a suboptimal way to do error correction. All these responses are generated in parallel, so we do not really learn from past mistakes; we can just have the model generate the same wrong predictions again and again.

In this part about inference time self-improvement, I will talk about techniques using large language models to iteratively improve their own response for a given task. This will align better with humans' error correction process.

The first papers about these ideas include Reflection and Self-Refine. In this process, there are two important steps after generating each solution. After the model generates the solution, the model will also generate some feedback based on what it observes. In this step, it can use external evaluation when available. In the original Reflection paper, they focus more on the agentic setup, where the LLM, as the agent, will propose actions to the environment. The environment will give the model some kind of changes of the observations. This will be an external signal to tell the model whether the current state is promising. Based on this model-generated reflection feedback and external observations, the large language model will refine its output to revise the next prediction step given both internal and external signals.

In the Reflection paper, they show that self-reflection and self-refinement work pretty well, especially when we can have a scheme so that the model can utilize high-quality evaluation or when the external signals are very reliable. For example, in the case of ALFWorld, it is an agent navigation task. There will be clear signals about observations at each step. They also evaluate their approach on HotPotQA, but they kind of repurpose this QA task into an agent environment. After the model generates the solution, they assume that the environment will give a signal about whether the current solution is correct or not. This is why you can keep seeing improvement with more trials. We will revisit this assumption later.

If we think about this self-improvement loop for applications, code generation is a pretty natural use case. When we are writing code, we also debug our code better within an IDE. We do not just write the code and stop. We actually rely on this interactive loop when we are trying to investigate code execution results and see whether it makes sense and which parts we should revise later. This is also one fundamental idea of recent coding agents.

In our paper on self-debugging, we also do a deeper dive into what kind of feedback formats will be helpful for the model to better correct its own mistakes. For example, the most simple feedback message is a short universal information about whether the current code is correct or not, without more information. For unit test feedback, we also include the execution results, like whether the current unit test has passed or whether there are any runtime errors. For code explanation, at each step, we also ask the model to self-generate some line-by-line explanation of the implementation in natural language. This idea is motivated by human debugging, trying to ask the model to see what it's trying to do in the code. Finally, in the trace feedback, we ask the model to perform some line-by-line simulation of the execution trace by itself. This is also one way of debugging by human programmers.

Empirically, we evaluated the latest large language models at the time of paper publication last year. We can see that with this self-debugging loop, it consistently improves performance across different large language models of different capabilities. If we give more informative feedback, it can further improve debugging performance.

Given all this discussion, the question is how we can best utilize the token budget by integrating all these different methods together. The fundamental question is understanding how to balance the inference budget for generating multiple samples in parallel or sequentially. This is a difficult question because it really depends on the task and the model. In essence, it's about whether the model for evaluation is good at self-reflection and correction for your specific task.

Here, I'm showing an example study from my colleagues at Google, where they are trying to find the optimal way to scale this token budget to solve math problems. In these specific experiments, they trained a model specialized at correcting math solutions. For different difficulty levels of problems, they study the optimal ratio to perform parallel generation versus sequential generation. The concrete numbers will really vary among different models. The overall conclusion is that for simple problems, the model can benefit more from self-correction because it knows more clearly whether the current solution is wrong and how it should revise. For harder problems, there is a better point in the middle about how much you should perform parallel generation and sequential refinement. With this kind of compute optimal factor for different task difficulties, they show that this compute optimal curve can also scale better than complete parallel generation.

When we think about inference time compute, another factor we should consider is the model size. Intuitively, with the same FLOPs budget, we can sample many more solutions from a lighter model. If a more expensive model does not perform much better than a cheaper model, then it will not be optimal to do inference by calling the more expensive model. From this empirical study from the paper "Inference Scaling Laws," they show that the optimal model with different inference budgets can be different. When you have a smaller inference time budget, maybe you want to rely more on lighter models. When you have more budget, you can utilize more expensive models, which can give you a boost on very challenging problems, where with smaller models, it would be very hard to come up with the final solution anyway.
